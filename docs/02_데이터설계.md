## 0. 먼저, 데이터베이스 용어 3개

| 용어 | 뜻 | 엑셀로 치면 |
|---|---|---|
| **테이블 (table)** | 같은 종류의 정보를 모아둔 표 | 시트 하나 |
| **컬럼 (column)** | 표의 세로 항목 | 열 (이름, 연락처…) |
| **행 (row)** | 실제 데이터 한 건 | 가로 한 줄 |

**외래키(foreign key)** 는 "이 행은 저쪽 테이블의 이 행에 속한다"는 연결선입니다.
예: 회차 하나는 반복 일정 하나에 속합니다 → `sessions.schedule_id` → `schedules.id`

## 2. 테이블 정의

### 2-1. `profiles` — 사용자

Supabase가 제공하는 `auth.users`(로그인 정보)에 붙는 추가 정보입니다.
**비밀번호는 저장하지 않습니다.** Supabase가 알아서 관리합니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid (PK) | `auth.users.id` 와 동일 |
| `name` | text | **이름** — 가입 때 입력. 화면에는 **항상 `김*연` 으로 가려서** 표시 |
| `nickname` | text | **닉네임** — 화면에 보이는 이름. **전체에서 유일해야 함** (unique) |
| `avatar_url` | text | 프로필 사진 (**선택**. 없으면 이름 첫 글자) |
| `is_admin` | bool | **봉사모아 운영자 여부** (기본 false) |
| `attended_count` | int | 참석 확인 누적 (기본 0) |
| `unconfirmed_count` | int | ‘확인 못 함’ 누적 (기본 0, **비공개**) |
| `created_at` | timestamptz | 가입일 |

> 두 카운트는 명단에서 매번 조회되므로 예외적으로 캐시해둡니다. 정확한 값이 필요할 땐 `applications`에서 다시 셉니다.

#### ⚠️ `role` 컬럼을 없앴습니다 (중요)

원래 `role`에 `volunteer` / `center_admin` / `admin` 을 두려 했으나 **삭제했습니다.**

기획서 2-1장의 원칙은 "계정은 하나, 권한은 센터마다 다르다"입니다. 그런데 `center_admin`을 프로필에 저장하면 **같은 사실이 두 곳에 적히게 됩니다.**

```
profiles.role = 'center_admin'        ← 여기
center_members(center_id, role)       ← 그리고 여기
```

이러면 반드시 어긋납니다. 담당자에서 해임됐는데 `role`이 그대로 남거나, A센터에서는 소유자·B센터에서는 담당자인 사람을 한 값으로 표현할 수 없습니다.

**판정은 언제나 한 곳에서만 합니다.**

| 묻고 싶은 것 | 어디를 보나 |
|---|---|
| 이 사람이 센터 관리자인가 | `center_members`에 행이 있는가 |
| 이 센터에서 무슨 권한인가 | `center_members.role` (`owner`/`staff`) |
| `내 센터` 탭을 보여줄까 | `center_members` 행이 1개 이상인가 |
| 봉사모아 운영자인가 | `profiles.is_admin` |

운영자(`is_admin`)만 프로필에 남깁니다. 이건 센터와 무관한 서비스 전체 권한이라 다른 곳에 둘 데가 없습니다.

#### 이름은 받되, 전체를 보여주는 곳은 한 곳도 없습니다 (v2.1)

**봉사자에게 받는 것은 `이메일` · `이름` · `닉네임` 세 가지입니다.** 전화번호는 받지 않습니다.

| | 저장 | 화면 표시 |
|---|---|---|
| `name` | 김서연 | **`김*연`** — 어디서든 항상 가려서 |
| `nickname` | 뭉치엄마 | 그대로 (**전체에서 유일**) |
| 이메일 | hello@… | 봉사자에게는 안 보임. **센터 담당자끼리만** 서로 공개 |

**왜 이름을 다시 받나** — 한때 이름을 아예 없애고 닉네임만 두려 했으나, **현장에서 부를 이름이 없어집니다.** 보호소 마당에서 «달려라뭉치 님 오셨나요?» 를 부를 수는 없습니다.

**왜 그래도 가리나** — 실명 전체가 명단에 뜨면 그 화면을 캡처하는 순간 개인정보가 밖으로 나갑니다. `김*연` 이면 **현장에서 확인하기에 충분하면서** 유출돼도 피해가 없습니다.

#### 센터 명단에는 둘을 나란히 씁니다

```
김*연  뭉치엄마          ← 이름(가림) + 닉네임
이 센터 12번째 참여
```

같은 `김*연` 이 둘이어도 **닉네임이 유일하므로** 반드시 구분됩니다.

#### 닉네임은 전체에서 유일합니다 ⭐ v2.2

```sql
ALTER TABLE profiles ADD CONSTRAINT uq_nickname UNIQUE (nickname);
```

- 가입 화면과 변경 팝업에서 **입력하는 동안** 중복을 알려줍니다. 저장 버튼을 누른 뒤에 알려주면 그 자리에서 나갑니다
- 화면 검사만 믿으면 안 됩니다. **두 사람이 동시에 같은 닉네임으로 저장할 수 있습니다.** DB 제약이 최종 방어선입니다
- 최소 2글자
- 대소문자·공백만 다른 것도 같은 것으로 봅니다 → 저장 전에 `trim()` 하고 소문자 기준으로 비교하세요

> **왜 유일해야 하나** — 이름을 `김*연` 으로 가려서 보여주기 때문에, 닉네임까지 겹치면 **센터가 두 사람을 구분할 방법이 없습니다.** 현장에서 다른 사람을 부르는 사고가 납니다.

#### 이름은 바꿀 수 없습니다

`profiles.name` 은 가입 때 한 번 받고 **수정 불가**입니다. 봉사 당일 현장 확인의 기준이 되는 값이라, 마음대로 바꿀 수 있으면 기준이 되지 못합니다. 오타를 냈다면 운영자에게 요청하는 경로만 둡니다.

#### `phone` 은 여전히 받지 않습니다

번호를 보관하는 순간 관리 책임이 생깁니다. 센터마다 «이 번호로 뭘 했는지» 를 관리해야 하고, 유출되면 즉시 신고 대상이며, 봉사가 끝나도 센터 엑셀과 단톡방에 남습니다. **혼자 만드는 첫 서비스가 감당할 무게가 아닙니다.**

| 상황 | 수단 |
|---|---|
| 봉사자가 센터에 물어본다 | **센터 대표 연락처** (신청 후 노출) |
| 봉사자가 당일 못 온다 | 취소 버튼 + 센터에 전화 |
| 센터가 신청자에게 알린다 | **자동 수단 없음** — 아는 연락처로 직접 (아래 ⚠️) |
| 담당자끼리 연락한다 | **서로의 이메일** (같은 센터 소속끼리만 공개) |

> ⚠️ **v2.1에서 회차 공지를 없앴습니다.** 그래서 센터 → 봉사자 방향으로 알릴 자동 수단이 **없습니다.** 회차를 휴무 처리하면 봉사자 화면에 «센터 사정으로 취소됨 + 사유» 가 뜨지만, 앱을 열어야 봅니다. 휴무 팝업에 이 사실을 적어 직접 연락하도록 안내합니다.

#### `unconfirmed_count` 는 공개 금지

노출되면 낙인이 됩니다. 센터 명단에서만 보이고 공개 프로필에는 절대 넣지 않습니다.

#### 프로필 사진 `avatar_url`

- **선택 항목입니다.** 가입 화면에서 받지 않고, 내 정보에서 나중에 넣습니다
- 없으면 **이름 첫 글자**를 원 안에 띄웁니다. 사진이 없어도 화면이 비어 보이지 않습니다
- Supabase Storage에 올리고 URL만 저장합니다
- **보이는 곳** — 신청자 명단, 후기, 공개 프로필, 헤더. 이름과 항상 같이 다닙니다

> 이름을 가려서 보여주므로 **프로필 사진이 현장 확인에서 실질적인 역할**을 합니다. 가입 후에 한 번 권하는 안내를 띄우면 등록률이 올라갑니다.

### 2-2. `centers` — 봉사센터

| 컬럼 | 타입 | 설명 |

#### `contact_phone` — 필수, 다만 공개 범위를 좁힙니다 ⭐ v1.9

**필수 입력으로 정했습니다.** 세 가지 역할을 하기 때문입니다.

1. **봉사자의 유일한 연락 수단** — 대화 기능이 없으므로 이게 없으면 급할 때 아무것도 못 합니다
2. **운영자의 실재 확인 수단** — 승인 심사에서 전화 한 통이 가장 확실합니다
3. **중복 센터 판별 기준** — 번호 완전 일치가 가장 정확한 신호입니다

**다만 아무에게나 보여주지 않습니다.**

**v2.4에서 공개 범위를 넓혔습니다.** 처음에는 신청을 마친 사람에게만 열어줬는데, **길을 못 찾는 사람이 물어볼 데가 없었습니다.** 신청 전에 확인하고 싶은 것(주차, 초등학생 동반, 우천 시 진행 여부)도 많습니다.

| 화면 | 연락처 |
|---|---|
| **센터 정보 팝업** | 보임 (누구나) |
| 신청 완료 · 내 봉사 › 봉사 상세 · 취소 팝업 | 보임 |
| 봉사 찾기 목록 카드 | 안 보임 (목록에 번호가 깔릴 이유가 없음) |

목록 카드에는 여전히 넣지 않습니다. 화면 하나에 번호 20개가 깔리면 **긁어가기 쉬워집니다.** 센터 정보를 한 번 열어야 보이게 하는 것만으로 대량 수집은 충분히 번거로워집니다.

같은 이유로 등록 화면에 안내를 답니다.

> 개인 휴대폰 번호라면 안심번호나 업무용 번호를 쓰시는 편이 좋습니다. 한번 알려드린 번호는 회수할 수 없습니다.

> **센터 대표번호는 개인정보가 아닙니다** — 기관의 연락처이기 때문입니다. 다만 위처럼 개인 번호를 쓰는 경우가 실제로 많아, 제도가 아니라 **설계로** 보호합니다.

#### 중복 센터 방지

같은 보호소를 두 사람이 각각 등록하면 봉사자가 혼란스럽고 명단이 갈라집니다. 승인의 가장 큰 목적입니다.

- DB로 완전히 막을 수는 없습니다 (이름 표기가 조금씩 다름)
- 대신 **운영자 승인 화면에서 유사 센터를 찾아 보여줍니다**
- 판정 기준: `contact_phone` 완전 일치 / `address` 유사 / `name` 유사
- 이름 유사도는 PostgreSQL의 `pg_trgm` 확장으로 처리 (Supabase에서 켤 수 있음)
- **최종 판단은 사람이 합니다**

### 2-3. `center_members` — 센터 담당자

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid (PK) | |
| `center_id` | uuid (FK → centers) | |
| `profile_id` | uuid (FK → profiles) | |
| `role` | text | `owner` / `staff` |
| `created_at` | timestamptz | |

제약: `unique(center_id, profile_id)`

**규칙**

- 센터 등록 신청자는 자동으로 `owner`가 됩니다
- `owner`는 **정확히 1명**입니다 → 마지막 owner 삭제는 거부

#### 소유권 이전 ⭐ v2.1

최종 권한자가 바뀔 때를 위한 장치입니다. 담당자가 그만두거나 센터를 넘길 때 반드시 필요합니다.

```
한 트랜잭션 안에서
  현재 owner 행  → role = 'staff'
  대상 staff 행  → role = 'owner'
```

- **되돌릴 수 없습니다.** 넘긴 뒤에는 새 소유자만 다시 넘길 수 있습니다
- 화면에서 **두 번 확인**합니다 (대상 선택 → 최종 확인)
- 대상은 **이미 담당자인 사람만** 고를 수 있습니다. 외부인에게 바로 넘길 수 없습니다
- 넘기면 새 소유자에게 알림이 갑니다
- 반드시 트랜잭션으로 묶으세요. 중간에 끊기면 **소유자가 0명이거나 2명**이 됩니다
- `owner`만 **요청 승인·해임·역할 변경·센터 정보 수정**이 가능합니다
- `staff`는 일정 등록·수정, 회차 관리, 신청자 명단 조회가 가능합니다
- 행이 삭제되면 그 사람은 **즉시** 센터 데이터에 접근할 수 없습니다 (RLS가 실시간으로 막음)

#### 나가기 · 내보내기

| 누가 | 행위 | 조건 |
|---|---|---|
| `owner` | 담당자 제외 | 제한 없음 |
| `staff` | 자발 탈퇴 | 제한 없음 |
| `owner` | 자발 탈퇴 | **다른 사람을 `owner`로 올린 뒤에만** |

- 행만 삭제합니다. **그 사람이 만든 `schedules`·`sessions`는 그대로 둡니다** — `created_by`는 기록으로 남습니다
- 사람이 나갔다고 센터 운영이 멈추면 안 됩니다

### 2-5. `center_join_requests` — 관리자 등록 요청

**담당자가 되는 유일한 경로**입니다. 당사자가 센터를 찾아 요청하고 소유자가 승인합니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid (PK) | |
| `center_id` | uuid (FK → centers) | |
| `requester_id` | uuid (FK → profiles) | |
| `message` | text | 소유자에게 보내는 한 마디 |
| `status` | text | `pending` / `approved` / `rejected` / `cancelled` |
| `handled_by` | uuid (FK → profiles) | 처리한 소유자 |
| `handled_at` | timestamptz | |
| `created_at` | timestamptz | |

제약: `pending` 상태는 `unique(center_id, requester_id)` — 중복 요청 차단

#### 승인 화면에 함께 조회할 것

소유자가 판단할 근거입니다. **쿼리 하나로 같이 가져옵니다.**

```sql
-- 이 센터에서의 참여 이력 (가장 강력한 신호)
SELECT count(*) AS 참석횟수, max(s.session_date) AS 최근참여
FROM applications a
JOIN sessions s ON s.id = a.session_id
WHERE a.volunteer_id = :requester
  AND s.center_id  = :center
  AND a.status IN ('attended','unconfirmed');
```

| 항목 | 출처 |
|---|---|
| 이름 (가림) | `profiles.name` → `김*연` |
| 별명 | `profiles.nickname` |
| 이메일 (가림) | `auth.users.email` → `yuj****@naver.com` |
| 프로필 사진 | `profiles.avatar_url` |
| 우리 센터 참여 횟수·최근 참여일 | 위 쿼리 |
| 가입일 | `profiles.created_at` |
| **다른 센터 동시 요청 수** | `center_join_requests` 에서 `requester_id`로 count |

#### 위험 신호 규칙

| 조건 | 표시 |
|---|---|
| 이 센터 참여 이력 0 | 주의 |
| 가입 후 7일 미만 | 주의 |
| 대기 중인 다른 센터 요청 3건 이상 | **경고** (어뷰징 의심) |

#### 거절 기록은 화면에 안 보입니다

거절하면 목록에서 사라집니다. 소유자가 나중에 다시 볼 이유가 없고, 쌓이면 화면만 지저분해집니다.
**단 `rejected` 행은 DB에 남깁니다** — 30일 재요청 제한을 판정해야 하기 때문입니다.

#### 남용 방지

- `pending` 중복 불가 (제약으로 강제)
- `rejected` 후 **30일간 재요청 불가** — `handled_at + 30일` 검사
- 한 사람의 `pending` 요청이 **5건을 넘으면** 새 요청 차단

#### 승인 시

1. `center_members`에 **`role='staff'` 로만** 추가 (절대 `owner` 아님)
2. `status`를 `approved`로
3. **기존 담당자 전원에게 알림** — 몰래 추가되는 것을 막습니다

> `owner` 승격은 이 흐름으로 불가능합니다. 별도 화면에서 기존 소유자가 명시적으로 올려야 합니다.

### 2-5. `schedules` — 반복 일정 ⭐

이전 버전의 `programs`를 대체합니다. **활동 종류가 아니라 "언제 봉사를 받는가"** 만 담습니다.

예: `2026.01.02 ~ 2026.02.03 / 매주 월·화·수 / 10:00~17:00 / 정원 8명`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid (PK) | |
| `center_id` | uuid (FK → centers) | |
| `title` | text | 관리용 라벨. "2026년 상반기 정기봉사" |
| `repeat_start_date` | date | **2026-01-02** |
| `repeat_end_date` | date | **2026-02-03** |
| `repeat_weekdays` | int[] | 0=일 … 6=토. 월·화·수 → `{1,2,3}` |
| `start_time` | time | 10:00 |
| `end_time` | time | 17:00 |
| `capacity` | int | 회차당 정원 8 |
| `location_text` | text | 집합 장소 |
| `open_days_before` | int | 며칠 전부터 신청 받을지 (기본 14) |
| `status` | text | `active` / `paused` / `archived` |
| `created_by` | uuid (FK → profiles) | **만든 담당자** |
| `updated_by` | uuid (FK → profiles) | 마지막으로 고친 담당자 |
| `updated_at` | timestamptz | |
| `created_at` | timestamptz | |

#### 담당자가 여러 명일 때

센터 데이터는 **담당자 전원이 공유**합니다. 개인별로 나뉘지 않습니다.

- 화면에 `최*진 님이 만든 일정 · 8월 6일 등록 · 마지막 수정 8월 7일 (권*재)` 를 표시합니다. 여러 명이 만들면 "이거 누가 왜 만든 거지?"가 반드시 생깁니다
- **중복 일정 경고** — 같은 센터에 `repeat_weekdays`가 겹치고 시간대가 겹치는 `active` 일정이 있으면 저장 전에 경고합니다. **막지는 않습니다.** 오전반/오후반처럼 의도적인 경우가 있습니다
- **동시 편집** — 1차는 last write wins. 저장 시 `updated_at`이 내가 읽어온 값과 다르면 "최*진 님이 방금 수정했습니다"를 띄웁니다. 실시간 잠금은 과합니다
- 담당자가 해임되면 `center_members` 행이 사라져 **즉시** 접근이 끊깁니다. 단, 그가 만든 일정의 `created_by`는 기록으로 남습니다

**규칙**

- **단발성 봉사** = 시작일과 종료일을 같은 날로 → 회차 1개만 생성
- 한 센터가 **반복 일정을 여러 개** 가질 수 있습니다 (평일반 / 주말반 / 특별 봉사)
- `repeat_weekdays`는 비어 있을 수 없습니다

#### 기간 제약 — 최대 1년

DB 레벨에서 강제합니다. 화면 코드만으로 막으면 우회가 가능합니다.

```sql
CONSTRAINT chk_repeat_range CHECK (
  repeat_end_date >= repeat_start_date
  AND repeat_end_date <= repeat_start_date + INTERVAL '1 year'
)
```

| 상황 | 결과 |
|---|---|
| 종료일 < 시작일 | 거부 |
| 시작일 + 1년 이내 | 통과 |
| 시작일 + 1년 초과 | 거부 |

**최대 회차 수 계산**

| 반복 요일 | 1년치 회차 수 |
|---|---|
| 주 1일 | 약 52개 |
| 주 3일 (월·화·수) | 약 156개 |
| 주 7일 (매일) | 약 365개 |

→ 최악의 경우 365개입니다. 회차 목록 화면에는 **월 단위 필터와 페이지 나누기**가 필요합니다.

#### 기간 만료 처리

- 종료일이 **30일 이내**로 다가온 `active` 일정을 찾아 대시보드 배너로 알립니다
- **연장 = 새 `schedules` 행을 만드는 것이 아니라, 기존 행의 `repeat_end_date`를 늘리는 것**입니다
  → 늘어난 구간의 날짜만 회차로 추가 생성합니다 (기존 회차는 그대로)
  → 이때도 `chk_repeat_range`가 다시 검사되므로, **시작일 기준 1년을 넘기면 연장이 거부됩니다.**
  이 경우엔 새 일정을 만들도록 안내합니다 (예: "2026년 하반기 정기봉사")

> ⚠️ **`title`은 봉사자에게 활동 종류로 보이지 않습니다.** 센터 관리자가 일정을 구분하기 위한 라벨입니다. 봉사자 화면에는 센터명과 날짜만 보입니다.

### 2-6. `sessions` — 회차 ⭐ 가장 중요

실제 날짜가 붙은 봉사 한 건. **참여 신청은 여기에 붙습니다.**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid (PK) | |
| `schedule_id` | uuid (FK → schedules) | |
| `center_id` | uuid (FK → centers) | 조회 편의를 위한 중복 저장 |
| `session_date` | date | 2026-01-05 |
| `start_time` | time | ← 일정에서 복사, **개별 수정 가능** |
| `end_time` | time | ← 복사, 개별 수정 가능 |
| `capacity` | int | ← 복사, 개별 수정 가능 |
| `location_text` | text | ← 복사, 개별 수정 가능 |
| `open_days_before` | int | ← 복사, 개별 수정 가능 (신청 오픈 시점) |
| `confirmed_count` | int | 확정 인원 (기본 0) |
| `status` | text | `open` / `closed` / `cancelled` / `done` |
| `cancel_reason` | text | "시설 점검" |
| `created_at` | timestamptz | |

제약: `unique(schedule_id, session_date)` — 같은 날 중복 생성 방지

#### ⚠️ `full` 상태를 없앴습니다 (중요)

원래 `status`에 `full`(정원 참)을 두려 했으나 **뺐습니다.** 같은 사실이 두 곳에 저장되기 때문입니다.

```
confirmed_count = 8, capacity = 8    ← 정원이 찼다
status = 'full'                       ← 정원이 찼다 (또)
```

동시 신청·취소가 오가면 둘 중 하나만 갱신되는 순간이 반드시 생기고, 그때 **"마감인데 신청이 되거나, 자리가 있는데 마감으로 보이는"** 버그가 납니다. 초보자가 가장 많이 겪는 유형입니다.

**마감 여부는 저장하지 않고 매번 계산합니다.**

| 화면 표시 | 판정식 |
|---|---|
| 신청 가능 | `status='open'` **AND** `confirmed_count < capacity` **AND** 신청 오픈됨 |
| 마감 | `status='open'` **AND** `confirmed_count >= capacity` |
| 휴무 | `status='cancelled'` |
| 센터가 닫음 | `status='closed'` |

`status`는 **사람이 바꾸는 것만** 담습니다 (센터가 휴무·마감 처리, 날짜가 지나 `done`). 인원에 따라 저절로 바뀌는 값은 넣지 않습니다.

> `confirmed_count` 자체도 사실 `applications`를 세면 나오는 값입니다. 다만 목록에서 회차마다 세면 느려지므로 **의도적으로 캐시**해둡니다. 캐시는 반드시 신청/취소 함수 안에서만 고칩니다.

#### 신청 오픈 시점을 회차에도 복사합니다

`open_days_before`를 `schedules`에만 두면 "이 회차만 미리 열어달라"를 처리할 수 없습니다. 다른 값과 마찬가지로 **회차에 복사해두고 개별 수정 가능**하게 합니다.

```
신청 오픈일 = session_date − open_days_before
오늘 < 오픈일  →  달력에 흐리게, "8월 1일부터 신청" 표시
```

#### 회차별 '할 일'은 두지 않습니다

한때 `task` 컬럼(그날 할 일)을 두는 안을 검토했으나 **뺐습니다.**

- 회차가 1년에 최대 365개인데 매번 손으로 적는 것은 현실적이지 않습니다
- 무엇을 할지는 **현장에서 배정**하는 것이 사설 센터의 실제 운영 방식입니다
- 안내가 필요하면 `centers.guide`(봉사 안내)에 한 번 적으면 됩니다
- 그날그날 다른 안내는 `centers.notice`(공지사항)로 처리합니다

> 나중에 필요해지면 `sessions`에 컬럼을 추가하면 되므로, 지금 넣지 않아 잃는 것은 없습니다.

#### 왜 일정 값을 복사해두는가

이게 설계의 핵심입니다. 복사해두면 **회차 하나만 예외 처리**할 수 있습니다.

- 1/26(월)만 휴무 → 그 행의 `status`를 `cancelled`로
- 1/27(화)만 정원 5명 → 그 행의 `capacity`만 5로
- 반복 일정 규칙은 그대로

복사하지 않고 매번 계산하는 방식이면 이 예외들을 감당할 수 없습니다.

#### 상태 전이

```
open ──(센터가 마감)──> closed
  │
  ├──(센터가 휴무)────> cancelled
  │
  └──(날짜가 지남)────> done
```

정원이 차고 비는 것은 **상태가 아닙니다.** `confirmed_count`와 `capacity`를 비교해 그때그때 판정합니다.

`done`은 **날짜가 지나면 자동으로** 바뀝니다.

> **1차에서는 `done` 자동 전환 작업(cron)을 만들지 않아도 됩니다.** 조회할 때 `session_date < 오늘` 이면 지난 회차로 취급하면 그만입니다. 배치 작업은 돌지 않으면 조용히 망가지는데, 초보자가 그걸 알아채기 어렵습니다. `done`은 나중에 통계가 필요해지면 그때 넣으세요.

#### ⭐ 계획됨, 아직 DB에 없음 — 시간 잠금 트리거 (2026-08-10, 4단계 설계)

**신청자가 1명이라도 있으면(`confirmed_count > 0`) `session_date`/`start_time`/`end_time`을 수정하려는 UPDATE를 트리거가 거부합니다.** 정원(`capacity`)은 이 트리거와 무관하게 언제든 수정 가능합니다.

- **신청자 0명**이면 시간도 정원도 자유롭게 수정
- **신청자 있으면** 시간만 잠기고, 바꾸려면 그 회차를 `cancelled` 처리(기존 휴무 처리 재사용)하고 새 회차를 만들어야 함
- 이유: 이미 신청한 사람에게 자동으로 알릴 수단이 없는 상태(2-11장)에서 시간이 조용히 바뀌면 사고가 남. 신청자가 0명이면 애초에 그 위험이 없으므로 막을 이유가 없음
- 화면에서도 막지만(신청자 있는 회차는 시간 입력칸을 안 보여줌), **UI 우회 방지를 위해 DB 트리거로도** 이중으로 막음
- 자세한 화면 흐름은 `docs/00_현재상태.md`의 "4단계 설계" 절 참고

> **값과 화면 문구는 다릅니다.** `unconfirmed` 는 화면에 **«기간 만료»** 로 씁니다. «확인 못 함» 은 사람이 뭘 못 한 것처럼 읽혀 낙인이 되지만, «기간 만료» 는 3일이라는 기한을 가리키는 말이라 덜 공격적입니다. DB 값은 바꾸지 않습니다.

#### ⭐ 계획됨, 아직 DB에 없음 — 신청 인원(동반자) (2026-08-10, 4단계 설계)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `party_size` | int, 기본 1 | 본인 포함 인원. `check (party_size between 1 and 50)` |
| `contact_phone` | text, null 허용 | **`party_size >= 2`일 때만** 값이 들어감. 노쇼 방지용, `profiles`엔 절대 저장 안 함 |

`party_size`가 2 미만으로 줄면 `contact_phone`은 자동으로 지웁니다. 신청 함수(`apply_to_session`)의 정원 체크는 `confirmed_count + party_size <= capacity`로 바뀌고, `party_size >= 2`인데 `contact_phone`이 없으면 함수가 거부합니다. 자세한 화면 흐름은 `docs/00_현재상태.md`의 "4단계 설계" 절 참고.

#### 상태 전이

```
신청 ──> confirmed ──(봉사자 취소)────────> cancelled (by volunteer)
             │       (센터가 휴무 처리)───> cancelled (by center)
             │
             ├──(봉사자가 3일 내 '참석 완료')──> attended
             └──(3일 지남, 자동)────────────> unconfirmed
```

`cancelled_by`를 나누는 이유는 **화면에 쓰는 말이 달라야 하기 때문**입니다. 내가 취소한 것과 센터 사정으로 취소된 것을 똑같이 "취소됨"이라고 쓰면 봉사자는 자기가 취소한 줄 압니다.

| `cancelled_by` | 내 봉사 목록 표시 |
|---|---|
| `volunteer` | `취소함` (회색) |
| `center` | `센터 사정으로 취소됨 · 시설 점검` (주황) |

#### 재신청 시 유의

`unique(session_id, volunteer_id)` 때문에 **취소한 회차에 다시 신청하면 INSERT가 실패합니다.** 새 행을 넣지 말고 기존 행을 `confirmed`로 되돌리고 `cancelled_at`·`cancelled_by`를 비웁니다 (UPSERT). 이걸 놓치면 "취소했다가 마음 바뀐 사람"이 영영 다시 신청할 수 없습니다.

#### 참석 확인은 봉사자가 한다 ⭐

**센터는 출석 체크를 하지 않습니다.** 매 회차 명단을 찍는 일은 결국 안 하게 되고, 안 하면 죽은 기능이 됩니다.

| 항목 | 값 |
|---|---|
| 확인 주체 | 봉사자 본인 |
| 확인 기한 | `session_date` + **3일** |
| 기한 초과 | `unconfirmed`로 자동 전환 |
| 불이익 | **없음** (기록만) |

- 매일 도는 작업이 `session_date + 3일`이 지난 `confirmed` 행을 `unconfirmed`로 바꿉니다 (Supabase 스케줄)
- `attended` → `profiles.attended_count` +1 / `unconfirmed` → `unconfirmed_count` +1
- **센터의 노쇼 신고 기능은 1차에 없습니다.** 봉사자 확인과 충돌하면 누가 맞는지 판정해야 하고, 그 순간 센터에게 다시 일이 생깁니다
- 지금은 제재가 없지만 **데이터를 쌓아두어** 나중에 정책을 붙일 수 있게 합니다

> 노쇼를 실제로 줄이는 건 제재가 아니라 **쉬운 취소**입니다. 취소 버튼을 잘 보이게 두고 불이익이 없다고 명시합니다.

> **대기(waitlist)는 만들지 않습니다.** 정원이 차면 그냥 신청할 수 없습니다.
> 취소자가 생기면 자리가 다시 열리고, 먼저 신청하는 사람이 가져갑니다.
> 대기 기능은 "언제 확정될지 모르는 상태"를 만들어 알림 없이는 오히려 불편합니다. 알림이 생긴 뒤에 다시 검토합니다.

**규칙**

- 후기 작성은 **선택**입니다. 안 써도 참석 기록은 남습니다

#### 수정·삭제 권한 — 작성자에게 있습니다

이전 설계(아무도 못 고침)를 **뒤집었습니다.**

| 주체 | 권한 |
|---|---|
| **작성자** | 수정 · 삭제 |
| 센터 | 신고만 |
| 운영자 | `hidden` 처리 |

이유 셋입니다.

1. 잘못된 정보를 고쳐야 합니다 (버스 번호를 틀리게 적으면 계속 헤맵니다)
2. **개인정보를 실수로 적었을 때 본인이 지울 수 있어야 합니다.** 법적으로도 보장돼야 하는 권리입니다
3. 되돌릴 수 없으면 아예 안 씁니다. 후기가 안 쌓이면 기능 자체가 무의미해집니다

- 삭제는 **soft delete**(`deleted_at` 기록)입니다. 신고 이력 대조를 위해 데이터는 남깁니다
- 조회 쿼리는 항상 `deleted_at IS NULL AND status = 'visible'` 조건을 답니다

#### 운영자가 숨길 수 있는 기준

> "안 좋은 후기를 없애고 좋은 것만 남긴다"는 **하면 안 됩니다.**
> 나쁜 후기가 하나도 없는 페이지는 아무도 믿지 않습니다. 부정적인 후기가 있어야 긍정적인 후기가 믿을 만해집니다.

| `hidden` 처리 O | 처리 X |
|---|---|
| 욕설·비방 | "생각보다 힘들었어요" |

### 2-13. 신청자 직접 추가 ⭐ v2.1 신설

|---|---|---|

- 참석 확인과 후기는 쓸 수 없습니다. 누를 사람이 없기 때문입니다

| 항목 | 본인 신청 | 직접 추가 |
|---|---|---|
| 이름 | `김*연` | `한*름` |
| 닉네임 | 뭉치엄마 | (없음) |
| 신청 방법 | 본인이 신청 | 센터가 직접 추가 |
| 신청일 | 8월 8일 오후 2:14 | 8월 9일 · 권*재 님이 추가 |
| 메모 | (없음) | 최*진 님 지인 · 전화로 신청 |

**제외했을 때의 처리**

```
본인 신청  → applications.status = 'cancelled', cancelled_by = 'center'
             봉사자 화면에 «센터 사정으로 취소됨» 으로 표시
직접 추가  → 행을 삭제 (계정이 없어 알릴 대상이 없음)
둘 다      → confirmed_count -1
```

- 되돌릴 수 없으므로 **한 번 더 묻습니다**
- ⚠️ 본인 신청을 뺄 때는 **알림이 없어 봉사자가 앱을 열어야 압니다.** 팝업에 «미리 알려주세요» 를 적어둡니다
- 남용을 막기 위해 누가 뺐는지 기록합니다 (`cancelled_by_member_id`)

> **왜 필요한가** — 사설 센터는 여전히 전화와 카톡으로 신청을 받습니다. 그 사람들을 명단에 못 넣으면 **센터는 봉사모아와 엑셀을 둘 다 쓰게 되고, 그러면 봉사모아를 안 씁니다.** 성공 기준이 «엑셀 대신 봉사모아로 운영» 인 이상 이 기능은 선택이 아닙니다.

## 3. 반드시 처리해야 할 규칙 7가지

초보자가 여기서 가장 많이 사고를 냅니다. ⑥·⑦은 검토 중 빠져 있던 것을 새로 채웠습니다.

### ① 정원 초과 방지 (동시 신청)

정원 8명에 7명이 찼는데 두 사람이 **동시에** 신청 버튼을 누르면, 둘 다 "1자리 남음"을 읽고 둘 다 통과합니다 → 9명.

**해결:** 화면 코드에서 세지 말고 **DB 안의 함수(Postgres function)에서 한 번에** 처리합니다.

```
1. 회차 행을 잠근다 (SELECT ... FOR UPDATE)
2. status 가 'open' 인지, 신청 오픈일이 지났는지 확인
3. confirmed_count < capacity 인지 확인
4. 여유가 없으면 → 신청 거부 ("이미 마감됐습니다")
5. 시간 겹침 검사 (아래 ①-2)
6. 통과하면 → confirmed 로 신청 생성 (있던 행이면 UPSERT)
7. confirmed_count 를 +1
8. 잠금 해제
```

취소가 발생하면 `confirmed_count`를 -1 합니다. **그 자리는 먼저 신청하는 사람이 가져갑니다.**

> `status`는 건드리지 않습니다. 마감 여부는 `confirmed_count >= capacity`로 매번 판정합니다 (2-6장 참조).

→ 실제 SQL은 개발 단계에서 작성합니다. **지금은 "이 문제가 존재한다"는 것만 기억하세요.**

### ①-2 시간 겹침 방지

**"하루 1건 제한"은 채택하지 않았습니다.** 오전에 유기견 산책, 저녁에 배식 봉사 같은 정상적인 경우까지 막기 때문입니다. 대신 **물리적으로 불가능한 경우만** 막습니다.

정원 검사와 **같은 DB 함수 안에서** 이어서 검사합니다.

```sql
-- 신청하려는 회차와 시간이 겹치는 confirmed 신청이 있는지
SELECT 1
FROM applications a
JOIN sessions s ON s.id = a.session_id
WHERE a.volunteer_id = :me
  AND a.status = 'confirmed'
  AND s.status  = 'open'          -- ★ 휴무·마감된 회차는 겹침으로 보지 않음
  AND s.session_date = :target_date
  AND s.start_time < :target_end
  AND s.end_time   > :target_start
```

- 한 행이라도 나오면 신청 거부하고, **겹치는 봉사가 무엇인지** 함께 알려줍니다
- 겹치지 않으면 같은 날 두 곳도 허용합니다
- 이동 시간은 계산하지 않습니다. 과한 개입이고 판단은 봉사자 몫입니다

> ⚠️ **`s.status = 'open'` 조건을 빠뜨리면 안 됩니다.** 센터가 휴무 처리한 회차의 신청은 `cancelled`로 바뀌지만(아래 ⑥), 처리 전 잠깐이라도 `confirmed`로 남아 있으면 **가지도 않을 봉사 때문에 멀쩡한 신청이 막힙니다.** 봉사자는 왜 막혔는지 알 수 없어 그냥 나갑니다.

> `start_time < target_end AND end_time > target_start` 가 구간 겹침의 표준 판정식입니다. 부등호를 `<=`로 쓰면 13:00 종료와 13:00 시작을 겹친다고 판정하니 주의하세요.

### ② 회차 생성 — 기간 방식

```
repeat_start_date 부터 repeat_end_date 까지 하루씩 훑으며
  그 날의 요일이 repeat_weekdays 에 있으면 → 회차 1개 생성
```

- 예: 2026.1.2 ~ 2.3, 월·화·수 → 1/5, 1/6, 1/7, 1/12, 1/13, 1/14 … 2/2, 2/3 → **총 14개**
  (시작일 1/2는 금요일이라 제외됩니다. 종료일 2/3은 화요일이라 포함됩니다)
- **8주치 자동 연장 같은 건 하지 않습니다.** 기간이 끝나면 끝입니다
- 기간 종료 30일 전부터 대시보드에 "일정 연장하시겠어요?" 를 띄웁니다
- 과거 날짜는 생성하지 않습니다 (오늘 이전은 건너뜀)
- **기간은 시작일로부터 최대 1년** — 최악의 경우 365개 회차가 한 번에 생성됩니다.
  회차를 하나씩 넣지 말고 **한 번의 쿼리로 일괄 삽입**해야 합니다 (`generate_series` 사용)

### ③ 반복 일정 수정 시 기존 회차 처리

```
미래 회차 중 신청자가 0명       → 새 규칙으로 갱신 O
미래 회차 중 신청자가 1명 이상   → 그대로 둔다 X
과거 회차                       → 절대 건드리지 않는다 X
```

수정 화면에서 **"신청자가 있는 3개 회차는 변경되지 않습니다"** 라고 알려주는 것이 중요합니다.

기간을 줄인 경우, 잘려나가는 날짜에 신청자가 있으면 **삭제하지 않고 경고**합니다.

### ④ 취소로 자리가 열렸을 때

**대기 명단을 두지 않습니다.** 자리가 열리면 그대로 `open` 상태가 되고, 먼저 신청하는 사람이 가져갑니다.

- 화면 코드에 `waitlist` 관련 분기를 넣지 않습니다
- 나중에 대기 기능을 넣더라도 `applications.status`에 값을 추가하면 되므로, **지금 미리 만들어 둘 이유가 없습니다**

### ⑤ 마지막 소유자 보호

`center_members`에서 `role='owner'`인 행이 0개가 되면 그 센터는 아무도 관리할 수 없게 됩니다.
**삭제·역할 변경 시 owner가 최소 1명 남는지 검사**해야 합니다. DB 트리거로 막는 것이 안전합니다.

### ⑥ 회차를 휴무 처리했을 때 신청자는 어떻게 되나 ⭐ 새로 추가

**설계에서 빠져 있던 구멍입니다.** 그리고 실제 운영에서 가장 먼저, 가장 자주 터지는 상황입니다.

> 8월 29일 회차에 6명이 신청해 있는데, 센터가 시설 점검으로 그날을 휴무 처리했습니다.
> 이 6명은요?

**규칙 — 같은 함수 안에서 한꺼번에 처리합니다.**

```
1. sessions.status = 'cancelled', cancel_reason 저장
2. 그 회차의 confirmed 신청을 전부
     status='cancelled', cancelled_by='center', cancelled_at=now()
3. confirmed_count = 0
4. (2차, 알림 붙은 뒤) 6명에게 알림 발송
```

**신청자를 그냥 두면 안 되는 이유**가 셋입니다.

1. 그 사람의 `내 봉사 › 다가오는`에 **없어진 봉사가 계속 남습니다**
2. 시간 겹침 검사에 걸려 **그날 다른 봉사를 신청하지 못합니다**
3. 봉사가 끝난 날 `참석 확인` 알림이 갑니다 — 열리지도 않은 봉사에

#### 1차에는 알림이 없습니다 — 그래서 화면으로 막습니다

이게 이 문제의 진짜 위험입니다. 봉사자는 휴무된 걸 **모르고 현장에 갑니다.** 첫 봉사가 헛걸음이면 그 사람은 다시 오지 않습니다.

알림을 만들지 않는 대신 세 곳에 장치를 둡니다.

| 어디 | 무엇 |
|---|---|
| **센터 휴무 처리 팝업** | `신청한 6명에게 알림이 가지 않습니다. 명단의 연락처로 직접 알려주세요.` + **명단 복사 버튼을 그 자리에** |
| **봉사자 `내 봉사`** | 취소된 건을 목록에서 지우지 않고 **주황 카드로 남깁니다** — `센터 사정으로 취소됨 · 시설 점검` |
| **취소된 건 정렬** | 다가오는 봉사 **맨 위**에 둡니다. 아래로 밀면 못 봅니다 |

> 휴무 처리 팝업에서 **명단 복사가 한 번에 되어야 합니다.** "따로 명단 보러 가서 복사해오세요"로 만들면 센터는 그냥 안 알립니다.

#### 되돌리기

휴무를 취소해 다시 열면 **신청은 자동으로 살아나지 않습니다.** 이미 다른 일정을 잡은 사람이 있기 때문입니다. 회차는 빈 상태(`open`, `confirmed_count=0`)로 열리고 선착순으로 다시 받습니다. 팝업에 이 사실을 적어둡니다.

---

### ⑦ 봉사자 취소는 언제까지 되나 ⭐ 새로 추가

**이것도 정해져 있지 않았습니다.** 지금 설계대로면 봉사 시작 1분 전에도 취소가 됩니다.

**규칙 — 봉사 시작 전까지는 언제든 취소할 수 있습니다.** 마감 시한을 두지 않습니다.

```
now() < (session_date + start_time)   →  취소 가능
그 이후                                →  취소 불가 (지난 봉사로 넘어감)
```

시한을 두지 않는 이유는 기획서와 같습니다. **노쇼를 줄이는 건 제재가 아니라 쉬운 취소**입니다. "전날 자정까지"로 막으면 당일 아침에 사정이 생긴 사람은 **취소하지 못하고 그냥 안 옵니다.** 센터 입장에서는 조용한 노쇼보다 아침에 온 취소 알림이 훨씬 낫습니다.

**대신 시점에 따라 말을 다르게 합니다.**

| 언제 | 취소 팝업 문구 |
|---|---|
| 2일 전까지 | `취소하면 그 자리는 다른 분이 바로 신청할 수 있습니다. 불이익은 없습니다.` |
| **하루 전 ~ 당일** | `센터가 이미 인원에 맞춰 준비했을 수 있어요. 취소는 지금도 되지만, 명단의 연락처로 한 번 알려주시면 큰 도움이 됩니다.` + **센터 연락처 표시** |

- 비난하지 않습니다. 취소 자체를 어렵게 만들면 조용한 노쇼로 바뀝니다
- 당일 취소에도 `unconfirmed_count`는 올라가지 않습니다. 취소는 노쇼가 아닙니다
- 취소하면 즉시 `confirmed_count -1` — 그 자리는 바로 다른 사람이 가져갈 수 있습니다

**봉사 시작 시각이 지나면 취소 버튼은 사라집니다.** 그 자리에 `참석 확인` 버튼이 들어옵니다.

## 4. 보안 — RLS (이걸 빠뜨리면 데이터가 다 털립니다)

Supabase는 **브라우저에서 DB에 직접 접근**합니다. 그래서 "누가 어떤 행을 볼 수 있는가"를 DB 자체에 걸어둬야 합니다. 이걸 **RLS(Row Level Security)** 라고 합니다.

> ⚠️ RLS를 안 켜면, 조금만 아는 사람이 **모든 봉사자의 이름과 전화번호를 통째로 가져갈 수 있습니다.** 개인정보 유출 사고입니다.

### 필요한 정책

| 테이블 | 정책 |
|---|---|
| `profiles` | 본인 행만 조회·수정. 센터는 자기 회차 신청자의 **`name`(가려서)·`nickname`·`avatar_url`만** 조회 |
| 이메일 | **같은 센터 담당자끼리만** 서로 조회. 봉사자에게는 노출 금지 |
| `centers` | `approved`인 곳은 누구나 조회. 수정은 해당 센터 `owner`만. `pending`은 신청자 본인과 운영자만 |
| `center_members` | 같은 센터 소속이면 조회. 추가·삭제는 `owner`만 |
| `center_join_requests` | 요청자 본인과 해당 센터 `owner`만 조회 |
| `schedules` | 조회는 누구나(승인 센터 한정). 생성·수정은 해당 센터 담당자만 |
| `sessions` | 위와 동일 |
| `applications` | 봉사자는 본인 신청만. 센터는 자기 센터 회차의 신청만 |
| `reviews` | `visible` + 미삭제만 조회. **수정·삭제는 작성자만.** 센터는 신고만 |
| `review_reports` | 신고자 본인과 운영자만 조회. 센터·작성자에게 노출 금지 |
| `favorites` | 본인 행만 조회·생성·삭제 |
| `sessions.notice` | 조회는 **그 회차 신청자와 센터 담당자만.** 작성은 담당자만 |

### 공개 화면에서 절대 나가면 안 되는 컬럼

RLS와 별개로 **쿼리에서 아예 빼는** 습관을 들입니다.

- `profiles.unconfirmed_count` — 노출되면 낙인이 됩니다
- `review_reports.*` 전부
- `centers.contact_phone` — **신청을 마친 봉사자와 센터 담당자에게만**
- `sessions.notice` — 그 회차 신청자에게만

> **실명과 봉사자 전화번호는 아예 저장하지 않으므로 나갈 것이 없습니다.** 남은 위험은 위 네 가지뿐입니다.

**모든 테이블에 RLS를 켜는 것을 기본으로 합니다.** 켜고 나서 필요한 것만 여는 방식이 안전합니다.

## 7. 책임 범위와 안전 ⭐ v2.6

### 무엇이 문제인가

봉사모아에 올라오는 곳은 **1365에 등록되지 않은 개인·소규모 센터**입니다. 공식 기관과 달리 이런 것이 없습니다.

| 공식 기관 | 봉사모아의 센터들 |
|---|---|
| 봉사시간 실적 | 없음 |
| 봉사확인서 | 없음 |
| **봉사자 상해보험** | **대부분 없음** |
| 사고 대응 매뉴얼 | 센터마다 다름 |

**보험이 가장 큽니다.** 봉사 중 다치면 처리할 방법이 마땅치 않습니다. 유기동물 봉사는 물림·긁힘·낙상이 실제로 일어납니다.

### 세 겹으로 나눕니다

| 누가 | 무엇을 |
|---|---|
| **봉사모아** | 봉사할 자리를 **연결**합니다. 활동을 운영하거나 감독하지 않습니다 |
| **센터** | 활동을 **진행**합니다. 현장 안전과 사고 대응을 맡습니다 |
| **봉사자** | 조건과 안내를 **확인하고** 참여합니다. 무리하지 않습니다 |

이 구분을 화면 네 곳에 같은 말로 적습니다. 말이 조금씩 다르면 나중에 «어디에는 이렇게 써 있던데» 가 됩니다.

### 어디에 무엇을 적나

| 시점 | 화면 | 내용 |
|---|---|---|
| 가입 | 약관 체크 밑 | 봉사모아는 자리를 **연결**합니다. 활동은 각 센터가 진행합니다 |
| 센터를 볼 때 | 센터 상세 · 센터 정보 | 개인·소규모 센터입니다. **보험 가입 여부** 표시 |
| **신청할 때** ⭐ | 신청 팝업 | 보험·실적 없음 + **동의 체크** ← 가장 중요 |
| 신청 직후 | 신청 완료 | 무리하지 마세요. 위험해 보이면 쉬셔도 됩니다 |
| 센터 등록 | 등록 신청 | 현장 안전은 센터가 맡습니다 + **동의 체크** |

**신청 팝업의 체크가 핵심입니다.** `applications.agreed_at` 에 시각을 남겨, 나중에 «몰랐다» 는 주장에 대응할 근거가 됩니다.

### 겁주지 않는 것이 안전에 더 좋습니다

경고를 세게 하면 두 가지가 일어납니다.

1. **봉사를 안 옵니다.** 서비스가 죽습니다
2. **읽지 않게 됩니다.** 매번 빨간 경고가 뜨면 사람은 그걸 «닫아야 하는 것» 으로 학습합니다

그래서 이렇게 합니다.

| 하지 않는 것 | 하는 것 |
|---|---|
| 빨간색 경고 | **차분한 회청색** (`.safe`) |
| 여러 화면에서 반복 | **결정하는 순간에 한 번** |
| «책임지지 않습니다» | «센터와 함께 해결합니다» |
| 위험을 나열 | **행동 지침** («무리하지 마세요») |

> 마지막 줄 «몸이 안 좋거나 위험해 보이면 언제든 쉬셔도 됩니다» 는 배려처럼 읽히지만, **실제로 사고를 줄이는 문장**입니다. 무리하다 다치는 경우가 가장 많습니다.

### 보험이 있는 센터는 강점으로

`has_insurance = true` 면 **초록색으로** 표시합니다.

- 보험이 있는 센터는 봉사자를 더 모을 수 있어 **가입 유인**이 됩니다
- 없는 센터가 불리해 보이지 않도록, 등록 화면에 «대부분의 개인 센터가 그렇습니다» 를 적습니다

### 사고가 났을 때

```
1. 센터가 먼저 대응          ← 현장을 가장 잘 압니다
2. 봉사자가 운영자에게 문의   ← 내 정보 › 문의·신고
3. 운영자가 기록·중재         ← 판정이 아니라 기록과 안내
```

**운영자는 판정하지 않습니다.** 봉사모아는 당사자가 아니므로 사실관계를 판단할 위치가 아닙니다. 기록을 남기고, 필요하면 센터 노출을 멈추는 것까지가 할 수 있는 일입니다.

### 앞으로 검토할 것

- **단체 상해보험** — 센터 수가 늘면 플랫폼이 일괄 가입하는 방법이 있습니다. 봉사자 1인당 연 몇천 원 수준입니다. 이게 되면 이 서비스의 가장 큰 차별점이 됩니다
- **미성년자** — 지금은 만 14세 미만 가입 불가 + 센터별 나이 제한뿐입니다. 자기신고라 한계가 있습니다
