### 이미 검토하고 결론 낸 것 (다시 묻지 않아도 됩니다)

구현하다 보면 걸릴 만한 것들입니다. 전부 알고 그렇게 정했습니다.

**① 인원 스테퍼로 남은 자리를 역산할 수 있는데 결정 15와 안 부딪히나**

부딪히는 것처럼 보이지만 **그대로 갑니다.** 결정 15의 이유는 "숫자는 조급함만 만듦"인데, 스테퍼는 남은 자리를 *보여주는* 게 아니라 **자기가 데려갈 인원을 정하는 도구**입니다. 역산하려면 의도적으로 여러 번 눌러야 하고, 거기까지 하는 사람은 이미 알고 싶은 사람입니다.

대안(+ 를 항상 활성화하고 제출할 때 거부)은 **더 나쁩니다** — 다 입력하고 신청을 눌렀는데 실패하는 게, 누를 때 바로 막히는 것보다 나쁩니다(작업 원칙: "되돌릴 수 없는 요청 전에 미리 막기").

**② 시간 잠금 트리거가 `confirmed_count > 0` 인데, 취소로 0이 되면 다시 풀리는 게 맞나**

**맞습니다. 의도된 동작입니다.** 지금 확정된 신청자가 없으면 시간을 바꿔도 피해자가 없습니다. 막으면 "한 명이 신청했다 취소한 회차가 영원히 잠기는" 불합리가 생깁니다.

취소한 사람 화면은 `applications`가 `session_id`로 `sessions`를 참조하므로 **자동으로 새 시간이 보입니다.** 이미 "취소함" 상태라 혼란도 없습니다.

> `confirmed_count`가 party_size 합이라 "신청 3건"이 아니라 "인원 5명"일 수 있지만, 트리거는 `> 0`만 보므로 판정에 영향 없습니다.

**③ `contact_phone` 보유 30일은 누가 지우나**

**008 SQL에 정리 함수(`purge_old_contact_phones()` 같은 것)까지 만들어 둡니다.** 단 **자동 실행(pg_cron)은 7단계에서** 겁니다.

이유는 `sessions.done` 자동 전환을 미룬 것과 같습니다 — "배치 작업은 돌지 않으면 조용히 망가지는데 초보자가 알아채기 어렵습니다"(2-6장). 함수만 있으면 필요할 때 손으로 한 번 돌릴 수 있고, 나중에 스케줄만 붙이면 됩니다.

**단, 6단계(실제 운영)에 들어가기 전에는 반드시 한 번 정리하거나 스케줄을 걸어야 합니다.** 사용자에게 "30일 후 삭제"라고 고지하기 때문입니다.

### 1. 신청 인원 (동반자)

**흐름**: `신청하기` → **1단계** "몇 분이 함께 하시나요?" (인원 스테퍼만, 다른 필드 없음) → `다음` → **2단계** 인원수에 맞는 완성된 폼이 뜸.

> 왜 2단계로 나눴나 — 인원을 늘릴 때 폼 중간에 필드(연락처 등)가 갑자기 나타나면 사용자가 거부감을 느낍니다. 처음부터 완성된 모양으로 보여주면 그 문제가 아예 없어지고, 개발도 조건부 렌더링보다 단순해집니다.

| 인원 | 2단계 폼 내용 |
|---|---|
| 1명 | 안전 안내 동의 → `신청하기` (지금과 동일) |
| **2명 이상** | ① "센터 담당자가 확인 전화를 드릴 수 있어요. 연락이 닿지 않으면 신청이 취소될 수 있습니다" 안내 → ② 대표 연락처(필수) → ③ 개인정보 동의 체크(펼치면 수집항목/목적/보유기간/거부시 불이익 4항목) → ④ 안전 안내 동의 → ⑤ 메모(선택, 기존 `note` 컬럼 재사용, 새 컬럼 아님) → `신청하기` |

**데이터**
- `applications.party_size` int, 기본 1, `check (party_size between 1 and 50)` (50은 화면 상한이 아니라 DB 방어용 — 화면엔 숫자 상한 없음, 정원이 자연스러운 상한이 됨)
- `applications.contact_phone` text, nullable. **2명 이상일 때만** 값이 들어감. `profiles`엔 안 넣음
- 인원을 나중에 2명 미만으로 줄이면 저장된 `contact_phone`을 **자동으로 지움** (필요 없어진 개인정보를 계속 들고 있지 않기 위해)

**함수/로직**
- `apply_to_session`: 정원 체크를 `confirmed_count + party_size <= capacity` 로 확장. 전체 거부(부분 승인 없음). **2명 이상인데 연락처가 없으면 서버(함수)에서도 거부** — 클라이언트 검증만 믿지 않음
- `cancel_application`: 감소량을 party_size만큼
- 새 함수 `update_application_party_size`: 늘릴 땐 정원 재확인 + (2명 이상으로 넘어가면) 연락처 필요, 줄일 땐 무조건 허용 + 2명 미만이면 연락처 삭제. "인원 변경" 화면도 신청 때와 같은 2단계 구조를 재사용
- 정원 초과로 못 늘릴 때: "+"버튼 비활성화 + "신청 인원이 정원을 초과해요" (남은 자리 숫자는 여전히 안 보여줌 — 결정 15 유지)
- 취소 후 재신청하면 인원 1로 리셋 (이전 인원 기억 안 함)
- 센터가 신청자를 **직접 추가**할 때(전화 신청 등)는 연락처 요구 안 함 — 관리자가 이미 아는 사람이므로
- 참석 확인·후기는 **대표 신청자 1인 기준 그대로**. 동반자는 이름조차 안 받으므로(익명 인원수만) 개별 기록 자체가 없음
- (4단계에서 만들 신청자 명단 화면 설계 시 주의) 정원 진행률은 **행 개수가 아니라 party_size 합**으로 계산해야 함

### 2. 센터 회차 관리 (정원 · 시간)

**핵심 규칙 — 신청자 유무로 갈림**

| 회차 상태 | 정원 | 시간·날짜 |
|---|---|---|
| 신청자 0명 | 자유 수정 | **자유 수정** |
| 신청자 1명 이상 | 자유 수정 (기존 신청자는 항상 유지, 정원을 신청자 수보다 낮춰도 안 쫓아냄) | **잠김** — 취소 후 새로 만드는 것만 가능 |

> 처음엔 "회차가 생기면 무조건 시간 잠금"으로 갔다가, 신청자가 0명이면 애초에 위험(혼란)이 없으니 그럴 필요가 없다는 걸 뒤늦게 발견해서 고쳤습니다. 이유가 있는 조건이니 "그냥 시간 다 잠그자"로 단순화하지 마세요.

**화면**
- 일정 등록: 시간 필드 옆에 "신청자가 생기면 이 회차의 시간은 수정할 수 없어요" 안내 (가볍게, 경고색 아님)
- 회차 목록: 각 줄에 연필 아이콘 → **작은 팝업**(별도 화면 이동 없음) → 팝업 제목에 **날짜+시간 둘 다** 표시(같은 날 오전/오후반이 있을 수 있어서 날짜만으론 구분 안 됨) → 정원 입력 → `저장`/`취소`
  - 신청자 0명이면 이 팝업에서 시간도 같이 편집 가능
  - 신청자 있으면 시간 옆에 자물쇠 아이콘만 있고, **탭/호버해야만** "신청자가 있어 수정할 수 없어요" 툴팁이 뜸(평소엔 안 보임 — 상시 노출 문구 없앰)
- 정원 표시: 초과 시 `6/2명` 같은 비율 대신 **"마감" 배지 + "신청 6명"**
- 회차 취소(기존 "휴무 처리" 그대로 재사용, 새 기능 아님): "신청자 N명의 신청도 함께 취소되고, 되돌릴 수 없습니다" + `취소하기` 버튼 하나뿐. **명단 복사 버튼은 없앴음**(전화번호 있는 사람은 나중에 만들 명단 화면에서 바로 보고 걸면 됨, 복사할 이유가 없음). 취소 후 **아무것도 자동으로 안 함** — 새로 만들고 싶으면 관리자가 직접 "새 회차 만들기"로 이동
- 여러 회차 **한번에** 수정하는 기능은 **이번엔 안 만듦**. 스케줄(반복 패턴) 자체를 고치면 신청자 0명인 미래 회차엔 자동 반영되는 기존 규칙(3장 ③)으로 대부분의 경우가 해결됨. 정말 필요해지면(6단계 실사용에서 나오면) 그때 범위선택 UI를 추가
- 같은 센터·같은 날짜·같은 시간에 회차를 또 만드는 것: **경고만 하고 막지 않음** (오전반/오후반처럼 의도적인 경우 허용, 기존 3장 설계와 동일)

**DB**
- `sessions`에 트리거 추가: `confirmed_count > 0`인 행의 `session_date`/`start_time`/`end_time`이 바뀌면 예외 발생 (UI 우회 방지용 이중 방어)

## 한 줄 정의

> **봉사모아는 사설 봉사센터와 봉사자를 연결해, 봉사 모집부터 신청·관리를 한곳에서 할 수 있게 해주는 플랫폼이다.**

**전략의 핵심** — 봉사자와 센터 양쪽이 다 없는 상태에서 시작하므로, **센터에게 먼저 쓸모 있는 도구**가 되어야 합니다. 센터는 지금 엑셀과 카톡으로 명단을 관리합니다. 그 고통을 해결하면 센터가 들어오고, 센터가 자기 봉사자를 데려옵니다.

## 확정된 큰 결정 19가지

| # | 결정 | 왜 |
|---|---|---|
| 1 | 활동을 쪼개지 않고 **센터 + 날짜**로 신청 | "산책 봉사"만 열면 급한 청소는 아무도 안 도와줌 |
| 2 | **대기 신청 없음** — 정원 차면 마감 | 알림 없이는 "언제 확정될지 모르는 상태"가 더 불편 |
| 3 | 반복 일정은 **기간(시작~종료), 최대 1년** | 무제한이면 회차 수백 개 |
| 4 | **참석 확인은 봉사자가** 봉사 후 3일 안에 | 센터에게 출석 체크를 시키면 결국 안 함 |
| 5 | **후기에 별점 없음**, 작성자가 수정·삭제 가능 | 소규모 센터는 별점 하나에 타격. 못 지우면 아예 안 씀 |
| 6 | **계정 하나**로 봉사자·센터 관리자 겸용 | 센터 관리자도 다른 곳에 봉사하러 감 |
| 7 | **하루 1건이 아니라 시간 겹침**만 차단 | 오전·저녁 두 곳은 정상적인 경우 |
| 8 | 로그인은 **이메일·비밀번호** (1차) | 카카오는 개발자 등록·심사가 필요해 배포가 늦어짐 |
| 9 | **로그인 없이 둘러보기** 가능, 신청할 때만 로그인 | 가입부터 요구하면 그 자리에서 나감 |
| 10 | 담당자 합류는 **요청 → 승인** 한 방향 | 이메일 초대는 나이 있는 담당자가 안 씀 |
| 11 | 날짜 선택은 **달력 하나**로 | 목록과 병행하면 오히려 헷갈림 |
| 12 | **웹 먼저**, 앱은 나중에 | 초기엔 하루에도 몇 번 고침. 심사가 끼면 못 함 |
| 13 | **봉사자 전화번호를 받지 않는다.** 이름은 받되 `김*연` 으로 가림 | 현장에서 부를 이름은 필요하지만, 전체 노출은 위험 |
| 14 | **센터 대표 연락처는 필수. 센터 정보에서 누구나 공개** | 신청 전에 물어볼 데가 있어야 함. 다만 목록 카드에는 안 넣음 |
| 15 | 봉사자에게 **남은 자리 수를 안 알린다** | 갈 수 있다/없다만 알면 충분. 숫자는 조급함만 만듦 |
| 16 | **무한 스크롤을 쓰지 않는다** | 목록이 끝없이 늘면 그 아래 있는 것에 영영 못 닿음 |
| 17 | **이메일 인증을 거쳐야 신청 가능** | 아무 주소로나 만든 계정을 걸러냄 |
| 18 | **봉사모아는 «연결», 센터는 «진행», 봉사자는 «확인»** | 보험이 없는 개인 센터라 역할이 분명해야 함 |
| 19 | **경고는 빨강 대신 회청색, 결정 시점에 한 번만** | 겁주면 봉사를 안 오고, 반복하면 안 읽음 |

## 개발 시 반드시 처리할 것 7가지

이걸 놓치면 사고가 납니다. 자세한 내용은 `02_데이터설계.md` 3장·4장.

1. **정원 초과** — 두 사람이 동시에 신청하면 9명이 됩니다. DB 함수 안에서 잠그고 처리
2. **시간 겹침** — 같은 시간대 중복 신청 차단. 검사 조건에 `sessions.status='open'`을 꼭 넣기
3. **RLS(행 수준 보안)** — 안 켜면 신청자 명단과 센터 연락처가 통째로 유출됩니다
4. **닉네임 unique 제약** — 이름을 가려 보여주므로 닉네임이 유일해야 두 사람을 구분합니다
5. **회차 일괄 생성** — 1년치면 최대 365개. 한 번의 쿼리로
6. **회차 휴무 시 신청자 전원 자동 취소** — 안 하면 봉사자 목록에 유령 봉사가 남고, 모르고 현장에 갑니다
7. **같은 사실을 두 곳에 저장하지 않기** — 그래서 `profiles.role`과 `sessions.status='full'`을 없앴습니다

카카오 로그인은 **배포된 도메인이 있어야** 개발자 콘솔에 등록할 수 있고, 항목에 따라 검수도 필요합니다. 첫 배포를 그 심사에 묶어두면 아무것도 못 합니다.

### «이야기» 로 바꿨다가 «후기» 로 되돌렸습니다

`후기`가 상품평에서 온 말이라 부담을 준다고 보고 `이야기`로 바꿨는데, **되돌렸습니다.**

| 바꿔보니 | |
|---|---|
| 뜻이 너무 넓다 | «이야기 남기기»가 무엇을 쓰라는 건지 흐립니다. 잡담인지 감상인지 후기인지 |
| 찾기 어렵다 | 봉사자가 다른 서비스에서 쓰던 말이 `후기`라, 어디를 눌러야 할지 한 번 더 생각하게 됩니다 |
| 부담은 별점이 만든다 | 평가 압박은 단어가 아니라 **별점**에서 옵니다. 그건 이미 뺐습니다 |

**익숙한 말이 이깁니다.** 부담을 덜어야 할 곳은 단어가 아니라 «안 써도 됩니다» 같은 안내문이었습니다.

### 왜 «기간 만료» 인가

`확인 못 함`은 **사람이 뭔가를 못 한 것**처럼 읽힙니다. 실제로는 3일이라는 기한이 지난 것뿐이고, 왔는데 버튼만 안 누른 사람이 대부분입니다.

`기간 만료`는 사람이 아니라 **기한**을 가리키는 말이라 낙인이 덜합니다.

### 왜 인증을 앞으로 옮겼나

예전에는 가입 버튼을 누른 **뒤에** 인증 메일을 보냈습니다. 그러면 비밀번호와 닉네임까지 다 만든 뒤에야 이메일 오타를 발견하고, **되돌릴 길이 없습니다.**

```
[이전]  이메일·비밀번호·이름·닉네임 → 가입 → 메일 확인 → (오타면 처음부터)
[지금]  이메일 → 인증번호 확인 ✓ → 비밀번호·이름·닉네임 → 가입
```

인증 전에는 아래 칸이 흐리게 잠겨 있어, **순서를 헷갈릴 수 없습니다.**

> Supabase 로는 `signInWithOtp` → `verifyOtp` → `updateUser({password})` 순서입니다. 6자리 코드 방식이라 메일함을 오갈 필요가 없습니다.

### 연락처를 여는 대신 목록에는 안 넣습니다

처음에는 신청을 마친 사람에게만 열어줬는데, **길을 못 찾는 사람이 물어볼 데가 없었습니다.** 주차·초등학생 동반·우천 시 진행 여부처럼 **신청 전에** 확인하고 싶은 것도 많습니다.

다만 목록 카드에는 여전히 넣지 않습니다. 한 화면에 번호 20개가 깔리면 긁어가기 쉬워집니다. **센터 정보를 한 번 열어야 보이게** 하는 것만으로 대량 수집은 충분히 번거로워집니다.

### 참석 확인 → 후기, 한 단계를 두는 이유

바로 «후기 쓰기» 화면으로 밀어넣지 않고 한 번 물어봅니다.

```
[참석을 확인할까요?]  →  [참석 확인이 끝났어요]
                          오늘 하루 고생 많으셨습니다
                          다녀오신 이야기를 짧게 남겨주시겠어요?
                          [후기 쓰기]  [다음에 할게요]
```

방금 다녀온 순간이 **가장 쓰고 싶은 때**지만, 화면을 강제로 띄우면 부담이 됩니다. 왜 필요한지(«처음 가는 분들은 먼저 다녀온 사람의 이야기를 가장 많이 봅니다») 를 알려주고 고르게 합니다.

### 안내문 규칙을 정했습니다

> **사용자가 «행동을 바꿀» 정보만. 두 줄, 65자 이내.**

문제는 길이가 아니라 **섞임**이었습니다. 실제 UI 문구와 제 설계 해설이 한 덩어리로 붙어 있어, 개발자가 «이걸 화면에 넣어야 하나»를 판단할 수 없었습니다.

- 설계 근거 → **HTML 주석**으로 (개발자만 봄)
- 시안 확인용 링크 → **`.devnote` 점선 상자**로 (지울 것)
- 남은 것만 실제 안내문

가장 심했던 회차 명단은 170자에 세 주제가 섞여 있었는데, 42자로 줄였습니다.

### 위험 동작에 «확인이 필요한 요청» 2단계 추가

담당자 승인 중 **위험 신호가 있는 요청**만 한 단계 더 묻게 했습니다.

> 승인하면 **박\*수 님이 지금 바로** 이 센터의 모든 신청자 명단을 보게 됩니다.
> 나중에 해임할 수는 있지만, **그동안 본 명단은 되돌릴 수 없습니다.**

담당자가 되면 명단 전체가 열리는데, 기존에는 «그래도 승인» 한 번이면 끝이었습니다.

### 중복 화면은 «한 컴포넌트»입니다

시안에서 화면 두 개로 그린 것이, 개발에서도 두 개면 안 됩니다. 세 쌍에 주석을 박아뒀습니다.

| 시안 | 개발 |
|---|---|
| 봉사 찾기 · 센터 전체 | `<CenterList limit={4} />` / `<CenterList />` |
| 다가오는 회차 명단 · 지난 회차 명단 | 한 화면 + `session_date` 비교 |
| 다가오는 봉사 상세 · 지난 봉사 상세 | 한 화면 + 상태 |

두 번 만들면 카드 하나 고칠 때 두 곳을 고쳐야 합니다.

`docs/시안점검.js` — 구조·문구·개인정보·동작·확인 단계 **22항목**을 한 번에 검사합니다.

## v2.6 — 보험과 책임 범위 (2026-08-09)

봉사모아에 올라오는 곳은 **1365에 등록되지 않은 개인·소규모 센터**입니다. 공식 기관과 다른 점이 셋인데, 지금까지 봉사시간만 다루고 **보험을 안 다뤘습니다.**

| | 공식 기관 | 봉사모아의 센터들 |
|---|---|---|
| 봉사시간 실적 | 인정 | 없음 (이미 고지 중) |
| 봉사확인서 | 발급 | 없음 (이미 고지 중) |
| **봉사자 상해보험** | 대개 있음 | **대부분 없음** ← 새로 다룸 |

유기동물 봉사는 물림·긁힘·낙상이 실제로 일어납니다.

### 역할을 셋으로 나눴습니다

| 누가 | 무엇을 |
|---|---|
| **봉사모아** | 봉사할 자리를 **연결**합니다. 활동을 운영하거나 감독하지 않습니다 |
| **센터** | 활동을 **진행**합니다. 현장 안전과 사고 대응을 맡습니다 |
| **봉사자** | 조건을 **확인하고** 참여합니다. 무리하지 않습니다 |

화면 여섯 곳에 **같은 말로** 적었습니다. 말이 조금씩 다르면 «어디에는 이렇게 써 있던데» 가 됩니다.

### 넣은 것

| 구분 | 내용 |
|---|---|
| 신청 팝업 | **안전 안내 카드 + 필수 체크.** 동의 시각 기록 (`applications.agreed_at`) |
| 센터 정보 | **봉사자 보험 가입 여부.** 있으면 초록색 강점으로 (`centers.has_insurance`) |
| 센터 상세 | «개인·소규모 센터입니다» 회청색 카드 |
| 신청 완료 | «무리하지 마세요. 위험해 보이면 쉬셔도 됩니다» |
| 센터 등록 | **«현장 안전은 센터가 맡습니다» 동의** + 안전 관리 안내 |
| 내 정보 | **문의·신고 창구** — 사고·센터와의 문제·신고 |
| 약관 팝업 | «봉사모아가 하는 일» 을 맨 위에 |

### 겁주지 않는 것이 안전에 더 좋습니다

경고를 세게 하면 두 가지가 일어납니다. **봉사를 안 오고**, **읽지 않게 됩니다.** 매번 빨간 경고가 뜨면 사람은 그걸 «닫아야 하는 것» 으로 학습합니다.

| 하지 않은 것 | 한 것 |
|---|---|
| 빨간색 경고 | **차분한 회청색** |
| 여러 화면에서 반복 | **결정하는 순간에 한 번** |
| «책임지지 않습니다» | «센터와 함께 해결합니다» |
| 위험을 나열 | **행동 지침** |

> 신청 팝업 마지막 줄 — **«몸이 안 좋거나 위험해 보이면 언제든 쉬셔도 됩니다»**
>
> 배려처럼 읽히지만 **실제로 사고를 줄이는 문장**입니다. 무리하다 다치는 경우가 가장 많고, «쉬어도 된다» 는 허락이 미리 있어야 현장에서 말을 꺼냅니다.

### 나중에 — 단체 보험

센터가 늘면 **플랫폼이 봉사자 상해보험을 일괄 가입**하는 방법이 있습니다. 1인당 연 몇천 원 수준입니다.

이게 되면 «보험 되는 유일한 사설 봉사 플랫폼» 이 되어, **지금 가장 약한 지점이 가장 큰 차별점**으로 바뀝니다.
